# .NET 10 migration

This document records the migration of the recovered application and recovered
library solution from .NET 6 to .NET 10. It describes the active build, not the
framework used by the original published package.

## Targets and SDK

| Component | Target |
| --- | --- |
| Main WPF application | `net10.0-windows`, `win-x64` |
| Recovered WPF/Windows libraries | `net10.0-windows` |
| Recovered non-UI libraries | `net10.0` |
| Verified SDK | `10.0.300` |

`global.json` requests SDK `10.0.100` with `latestFeature` roll-forward. This
keeps the copied project on .NET 10 while allowing a newer installed .NET 10
feature band such as `10.0.300`.

WPF projects use `Microsoft.NET.Sdk` plus `UseWPF=true`. Projects that call
Windows Forms APIs retain `UseWindowsForms=true`. The following extension-package
references were moved from 6.0.0 to 10.0.0:

- `System.Configuration.ConfigurationManager`
- `System.Diagnostics.PerformanceCounter`
- `System.Drawing.Common`
- `System.Security.Cryptography.ProtectedData`

## Dependency manifest

The packaged `lib/pvfUtility.deps.json` has a .NET 6 runtime target. Earlier
recovery builds copied that file over the SDK output after every build and
publish. That override has been removed.

The active `pvfUtility.deps.json` is now generated by SDK 10.0.300 and reports:

```text
.NETCoreApp,Version=v10.0/win-x64
```

The main BAML container references some assemblies that do not appear in C#.
The build therefore declares these dependencies explicitly:

- `DevExpress.Xpf.Controls.v24.1`
- `DevExpress.Xpf.PropertyGrid.v24.1`
- `DevExpress.Xpf.TypedStyles.v24.1`
- all vendored `DevExpress.Xpf.Themes.*.v24.1` assemblies

The clean generated manifest contains 133 libraries and includes all three named
DevExpress BAML dependencies. The old `.NET 6` manifest remains under `lib` only
as recovery provenance and is excluded from output.

Some release libraries select optional SQL providers or extensions by assembly
name. `PvfCode.Compatibility.RecoveredAssemblyResolver` runs only after normal
dependency resolution fails. It probes `AppContext.BaseDirectory`, validates the
requested assembly identity, rejects native DLLs, and loads the matching managed
assembly into the default load context. It does not search the original package,
`_analysis_extract`, `pvfUtility-old`, or any absolute external directory.

## DevExpress compatibility

DevExpress WPF 24.1 reads the private WPF `Popup._popupRoot` field through
reflection. On the original runtime this field was a wrapper exposing a private
`get_Value` method. In .NET 10 it is a direct `PopupRoot` reference. During the
first migrated startup, `PopupControlContainer` therefore failed with:

```text
System.NullReferenceException
  at DevExpress.Xpf.Bars.BarPopupBase.GetPopupRoot(Popup popup)
```

`PvfCode.Compatibility.DevExpressNet10Compatibility` is installed before any
DevExpress popup is constructed. It checks the runtime and reflected field shape,
then supplies DevExpress with a direct field getter and identity value getter.
No DevExpress DLL is patched or decompiled into the source solution.

This is intentionally narrow private-API compatibility code. It should be
removed if the vendored DevExpress runtime is replaced by a release that natively
supports the .NET 10 `Popup` field layout.

## Build and verification

From the copied `pvfUtility-recovered` directory:

```powershell
dotnet restore .\pvfUtility.sln
dotnet build .\pvfUtility.sln -c Debug --no-restore
```

This ordinary solution build is a compiler/IDE verification step. All runnable
and distributable local output is produced through the unified single-file
pipeline:

```powershell
.\scripts\Build-SingleFile.ps1
```

The primary solution contains the main application, all 22 recovered source
libraries, the Hybrid resource merger, and its regression project.
`SourceLibraries\pvfUtility.SourceLibraries.sln` remains
available when only the recovered library graph should be loaded or built.

Clean verification with SDK 10.0.300 completes with zero errors for both the
recovered source solution and the main WPF application.

The warnings are retained decompiler and compatibility warnings: nullable
annotations without original nullable context, obsolete APIs, platform analysis,
unused recovered fields, and ignored/discarded async calls. No warning was
suppressed as part of the framework migration.

The default runnable executable is generated at:

```text
artifacts\publish\local\Hybrid\Debug\win-x64\pvfUtility.exe
```

Run the UI regression check with:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File .\scripts\Test-RecoveredStartup.ps1 `
  -Configuration Debug `
  -OutputDirectory .\artifacts\publish\local\Hybrid\Debug\win-x64 `
  -SingleFile
```

The final verification ran this check repeatedly against Debug and Release
single-file publish output. Each run kept the
fully populated main window available for 15 seconds, found
`BarSubItemLinksubFile`, `FilelistLayoutPanel`, and `DocumentHost`, and observed
no error window. When a `recovered-source-libraries.txt` manifest is present, the
script also compares all 20 output DLL hashes with their source-project `.build`
products and checks the paths of modules loaded during startup. Published output
can be tested explicitly with:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File .\scripts\Test-RecoveredStartup.ps1 `
  -Configuration Release `
  -OutputDirectory <publish-directory>
```

## Remaining constraints

- The main application retains all 126 original compiled BAML documents in
  `Resources/pvfUtility.g.resources`. Default Hybrid builds source-compile two
  documents and supplement the remaining resources from that immutable baseline;
  Legacy builds use all 126 original BAML entries. See `BAML_RECOVERY.md` and
  `SOURCE_XAML_MIGRATION.md`.
- The default main runtime uses 20 recovered source assemblies. External managed
  dependencies, DevExpress commercial assemblies, native DLLs, themes, satellite
  resources, optional providers, and `Binary`-mode fallbacks remain under `lib`.
- Seven native DLLs and DevExpress commercial assemblies remain binary runtime
  dependencies.
- Recovery cannot reproduce original comments, PDB local names, source-control
  history, or byte-identical .NET 6 compiler output.
